# 同步更新方案：网页如何持续跟上政策变化

> 2026-10-24 23:41–23:58
> 起因：用户问"文件找到了，等后续更新的时候，网页可以同步抓取最新的吗"

---

## 一、先说实测结论（这决定了架构）

我实测了厦门三个官方站的响应头：

```
xm.gov.cn / hrss.xm.gov.cn / ylbz.xm.gov.cn
  → 无 ETag
  → 无 Last-Modified
  → 无 Content-Length（chunked）
```

**所以 HTTP 条件请求（If-Modified-Since / If-None-Match → 304）在这批站点上不可用。**

这否掉了一个偷懒方案（"下次带 If-None-Since 试试"）。**唯一可靠的增量路径是：重新下载 + 内容比对。**

第二个实测结论更关键：**这些页面每次抓取的原始字节并不完全相同**。原因是页面上有动态内容——访问时间戳、随机 token、计数器、同站推荐位。

如果直接比对原始哈希，**每次同步都会报一堆"变更"**，很快没人会看这个告警。必须做内容归一化。

## 二、三条同步通路

| 通路 | 触发时机 | 抓取范围 | 用户感知 | 适用 |
|---|---|---|---|---|
| **A · 构建期同步** | 定时任务（每日/每周） | 全部 25 个源 | 无感，访问时数据已最新 | **主力** |
| **B · 访问期检查** | 用户访问时 | 只探测 16 个时效性关键源 | 顶部提示"可能有新政策" | 补充 |
| **C · 人工复核** | 一键触发 | 全部 + 变更报告 | 无 | 发布前把关 |

### 关键设计决策：官网永远只读

**三条通路都不在用户等待路径上抓官网全文。**

理由：
- 抓官网慢（渲染型源要 5–15 秒），用户不会等
- 高频抓官方站不礼貌，且可能被限流
- 官网挂了不该导致我的页面挂

所以：**数据在用户访问前就已经抓好了**。网页读的是本地快照 + 预生成的 JSON。

## 三、已实现的同步器

`pipeline/sync.py`，三个命令：

```bash
python3 pipeline/sync.py check    # 轻量探测：只比对 16 个关键源，不落盘
python3 pipeline/sync.py sync     # 全量重抓 → 比对 → 落盘 → 重建库 → 跑断言
python3 pipeline/sync.py report   # 打印同步历史
```

### sync 的完整链路

```
探测（下载到 .probe 临时文件）
   ↓
归一化后比对 content_hash
   ↓
变了？
   ├─ 否 → 删除临时文件，记 unchanged
   └─ 是 → 备份旧快照（.bak-时间戳）→ 落盘新快照
              ↓
          重新抽取文本（PDF 走 PDFKit/OCR，HTML 走清洗，render 走 Playwright）
              ↓
          重建政策库 build_db.py
              ↓
          重建参数表与判定式 engine.py
              ↓
          三层状态反查 status_check.py
              ↓
          跑 120 条断言 assertions.py
              ↓
          全绿 → 允许发布
          有红 → 拒绝发布，报错退出
```

| 场景 | 归一化后哈希 | 判定 |
|---|---|---|
| 只改访问时间戳 | 相同 | ✅ 不误报 |

## 四、网页侧怎么呈现"同步状态"

页面不需要自己抓，只需要读一份预生成的 `policy_db/sync_state.json`：

```json
{
  "last_sync": "2026-10-24T23:52:10+08:00",
  "sources": {
    "xm-yb-2026-rate": {
      "sha256": "…",
      "fetched_at": "2026-10-24T23:52:10+08:00",
      "doc_number": "厦医保公告 2026年度职工基本医疗保险缴费率",
      "url": "https://ylbz.xm.gov.cn/…"
    }
  }
}
```

**页面顶部一行**（不打扰用户，但要能证明"我是新的"）：

```
数据同步至 2026-10-24 23:52 · 25 份官方文件 · 42 条条款 · 每条结论可点开原文核验
[查看同步日志]
```

**每张引用卡片底部**（已有）：
```
厦府规〔2022〕12号 第六条 · 抓取于 2026-10-24 22:39 · 快照 e76be654…  [打开原文]
```

**"同步日志"抽屉**（新增）：
```
2026-10-24 23:52  检查 16 个关键源  全部未变化
2026-10-24 22:41  同步 25 个源  变更 1（闽医保〔2026〕13号）  重建通过
2026-10-24 21:30  初始化  25 个源
```

这样"数据是最新的"不是一句宣传语，而是**用户可以点开验证的事实**。

## 五、参赛场景下的实际用法

评委在 10 月 25 日打开页面 → 看到"数据同步至 10-24 23:52"。

如果 11 月厦门出了新文件（比如 2027 年度职工医保费率公告）：

| 时间 | 发生什么 |
|---|---|
| 定时任务触发 | 探测 → 检测到 `xm-yb-2026-rate` 变更 → 落盘 → 重建 → 断言 |
| 断言检查 | 新费率若让某个回归锚点失效（如 B3 "2024 年查不到费率"），**断言变红 → 拒绝发布** |
| 人工确认 | 跑 `sync.py report` 看变更报告，确认是否影响结论 |
| 更新页面 | 部署新快照 + 新 `sync_state.json` + 新 `policy_db.json` |

**关键点**：如果新公告让某个结论变了但**没人发现断言失效**，那断言就白写了。所以断言必须覆盖"时点隔离"这类结构性不变量（B3/B6/B7/K7/L3/L4/N3/N4 等），而不只是当前数值。

## 六、诚实说明的限制

| 限制 | 现实 | 应对 |
|---|---|---|
| 官方站改版 | 抓取会失败 | 已列入 `DISABLED` 的源有明确理由记录；`check` 会报"不可达"，不会假装正常 |
| 扫描件 OCR | 慢（6 页约 40 秒） | 已做 OCR 保护：普通抽取不得覆盖已有 OCR 文本 |
| 税务参数表 | 动态壳，每次都变 | 已列入 `DISABLED`（会误报），改用省人社厅文件取数 |
| 新文件发现 | 靠人社局政策库列表页 | 该源已在 `CRITICAL` 里，列表新增条目会被哈希比对捕获 |
| 实时性 | 最多延迟一个同步周期 | 页面明示"数据同步至 XX 时间"，不假装实时 |
| 服务器不能跑 Playwright | 渲染型源抓不了 | 抓取在构建期做，产物（JSON）随页面部署，服务器只需读文件 |

**最后一条是关键**：如果参赛部署环境只能跑静态网页，同步抓取在**构建机上**完成，**服务器只读 JSON**。这让同步能力不依赖运行时环境。

## 七、这一轮新增的断言（U 组 13 条）

| 编号 | 断言 |
|---|---|
| U1 | 每个政策条目都有原文与文本双哈希 |
| U2 | 每个政策条目都有抓取时间戳 |
| U3 | 同步关键源覆盖职工/居民/长护险/基数/最低工资 |
| U4 | 不可用源均有明确理由（不写理由会被误当成"政策没更新"） |
| U5 | 税务参数表已列入不可用（动态壳会误报） |
| U6 | 同步探测无 .probe 残留 |
| U7 | 同步状态含 last_sync 与 history 字段 |
| U8 | 同步器命令入口齐备 |
| U9 | 判定式不引用已禁用源的条款 |
| U10 | 归一化消除时间戳与 token 的动态差异（不误报） |
| U11 | 归一化不掩盖真实数值变更（不掩盖） |
| U12 | 同步历史已记录 |
| U13 | 失效文件不参与任何判定式引用 |

## 八、这一轮抓到的自身缺陷（已修复并固化）

| 缺陷 | 根因 | 修法 |
|---|---|---|
| 探测残留 `.probe` 文件 | 异常退出未清理 | `cleanup_probes()` + 每次 main 开头清理 |
| 税务参数表每次误报变更 | 页面是动态壳 | 列入 `DISABLED` 并写明理由 |
| 渲染型源探测全失败 | render.py 输出命名与探测期望不一致 | 统一为 `.render.txt` |
| 渲染型源每次误报 | 正文含动态内容 | 归一化哈希 |
| `probe_path` 为 None 时崩溃 | 渲染分支不返回路径 | `_rm()` 安全删除封装 |
| **OCR 文本被空结果覆盖** | 普通抽取覆盖了扫描件文本 | 抽取失败不覆盖；自动重跑 OCR |
| **死链源永远在库里** | `build_db` 从历史 fetch 日志累积 | 改以 `fetch.py` 的 SOURCES 为唯一真源 |
| **失效文件仍在库里** | 库不读状态反查结果 | 直接读有效性元数据判定，且解耦循环依赖 |
| 库成员与状态反查循环依赖 | 库依赖 status_check.json，后者依赖库 | 失效判定下沉到快照层元数据 |

其中 **"OCR 文本被空结果覆盖"** 和 **"死链源永远在库里"** 是两个会静默污染数据的 bug——如果没做这次同步演练，根本不会发现。
